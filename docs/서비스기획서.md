# 무드 페어링 (Mood Pairing) — 서비스 기획서

---

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | 무드 페어링 (Mood Pairing) |
| 한 줄 소개 | 제목도 가수도 모르는 곡을, 문장으로 찾습니다. |
| 형태 | 반응형 원페이지 웹 서비스 (5개 섹션) |
| 배포 | Vercel |

지금의 기분·상황·취향을 자유롭게 문장으로 적으면, AI가 그 맥락을 해석해
**실존이 검증된 곡 3~5개**와 **그 순간을 위해 새로 쓰인 짧은 글**을 함께 건넨다.

---

## 2. 문제 정의

### 2-1. 검색은 이름을 알아야 작동한다

모든 음원 앱의 검색창은 곡명·가수명·앨범명이라는 **고유명사 입력을 전제**한다.
그런데 우리가 음악을 찾는 동기는 대개 이름이 아니라 **상태**다.

> "가사는 밝은데 멜로디는 쓸쓸한 곡"
> "후렴에서 터뜨리지 않고 끝까지 눌러 담는 곡"
> "연주자의 해석을 빼고 악보 그대로 친 연주"

말로는 분명히 설명되지만, 이 조건을 입력할 칸이 어디에도 없다.

### 2-2. 추천은 나를 학습하지만, 오늘의 나는 모른다

청취 이력 기반 추천은 누적된 평균값에 수렴한다.
이력이 적으면 부정확하고(콜드스타트), 이력이 많아도 **그날의 맥락을 반영할 입구가 UI에 없다.**
"어제의 나"와 "새벽 2시의 나"를 구분할 방법이 사용자에게 주어지지 않는다.

### 2-3. 플레이리스트는 남의 기준이다

'비 오는 날', '드라이브' 같은 큐레이션은 최대공약수로 만들어진다.
취향의 해상도가 높은 사용자일수록 걸러낼 것만 늘어난다.

---

## 3. 핵심 가치

| 가치 | 설명 |
|---|---|
| **자연어 = 검색어** | 고유명사가 아닌 문장·분위기·모순된 조건·개인 기준을 그대로 입력 |
| **환각 없는 추천** | AI가 제안 → 실제 음원 DB로 실존 검증 → 통과한 곡만 노출 |
| **곡 + 문장** | 저작권을 따질 필요 없는, 그 입력을 위해 새로 쓰인 문장을 함께 제공 |
| **바로 듣기** | 30초 미리듣기 · 앨범아트 · 원본 음원 링크 |

---

## 4. 타겟 사용자

**주 타겟** — 원하는 음악의 조건은 말로 설명할 수 있지만 검색어로 옮기지 못하는 사람.
즉, 취향의 해상도가 기존 검색 UI보다 높은 모든 사용자.

**부 타겟** — 청취 이력이 부족해 추천이 겉도는 신규·라이트 유저.

**설계 원칙** — 입력이 길고 구체적일수록 결과가 좋아지도록 설계한다.
까다로운 사용자가 페널티가 아니라 이점을 얻는 구조여야 한다.

## 5. 페이지 / 섹션 구성

상단 고정 네비게이션 + 앵커 스크롤. 모바일(768px 미만)에서는 햄버거 메뉴로 전환.

| # | 섹션 | 내용 |
|---|---|---|
| 1 | **홈 (Hero)** | 한 줄 소개, 문제 제기, "지금 찾아보기" CTA |
| 2 | **무드 페어링** | **핵심 기능.** 입력 폼(자유 텍스트 + 예시 칩 + 선택 옵션) → 결과 카드(무드 요약 / 곡 카드 / 창작 문장) → 조정 영역 |
| 3 | **이렇게 검색해보세요** | 좋은 입력 vs 아쉬운 입력 비교, 3단계 작성 가이드 |
| 4 | **검색 기록** | 열람 · 같은 문장으로 재검색 · 개별 삭제 · 전체 삭제 · 내보내기 |
| 5 | **FAQ · 만든 이유** | 동작 원리, AI 추천의 한계 고지, 데이터 처리 방침, 사용 기술 |

## 6. AI 기능 설계

### 6-1. 아키텍처 — 왜 2단계인가

LLM에게 곡을 추천하게 하면 **존재하지 않는 곡을 실존 가수 이름으로 지어내는 문제**가 생긴다.
이 서비스는 AI에게 "무엇을 찾을지"만 맡기고, **실존 여부는 실제 음원 데이터베이스가 판정**한다.

```
사용자 자연어 입력
      │
      ▼
[1] Claude API — 무드 해석 + 후보곡 N곡 + 검색 키워드 + 창작 문장
      │           (JSON Schema로 출력 형식을 강제)
      ▼
[2] iTunes Search API로 후보곡을 하나씩 대조 (병렬 조회)
      │           검증 실패한 곡은 조용히 버림
      ▼
[3] 통과한 곡만 화면에 → 앨범아트 + 30초 미리듣기 + 음원 링크
      │           통과가 2곡 미만이면 검색 키워드로 보충
```

**음원 API로 iTunes Search API를 택한 이유**

| | iTunes Search API | Spotify Web API |
|---|---|---|
| API 키 | **불필요** | 필요 (OAuth) |
| 30초 미리듣기 | **제공** | 신규 앱 차단 (2024-11-27) |
| 앨범 아트 | 제공 | 제공 |
| 한국 곡 | `country=KR` 지원 | 지원 |

### 6-2. 입력

- **자유 텍스트** (필수, 10~500자)
- **선택 옵션**: 가사 유무(상관없음 / 있음 / 없음), 곡 개수(3 / 5)
- **조정** (결과 확인 후, 선택): 추천 칩 클릭 또는 **자유 입력**
  → 사전 필터가 아니라 **사후 조정**이라 자연어 흐름을 깨지 않는다.
  칩은 예시일 뿐이고 "드럼이 더 또렷했으면" 같은 문장도 그대로 반영된다.

### 6-3. 출력

| 필드 | 내용 |
|---|---|
| `mood_summary` | 입력을 어떻게 읽었는지 한 문장 |
| `tracks[]` | 검증된 곡 — 제목, 가수, 앨범아트, 미리듣기 URL, 음원 링크, 추천 이유 |
| `original_text` | 이 순간을 위해 새로 쓰인 2~3문장 |
| `keywords[]` | 음원 앱·유튜브에 그대로 넣어볼 수 있는 검색어 3개 |

**문장은 인용이 아니라 창작이다.**
기존 문학을 인용하면 (a) 사후 70년 저작권 보호 대상이 다수이고,
(b) LLM이 인용문을 실존 작가 이름으로 지어내는 오귀속 위험이 매우 크다.
그래서 인용 대신 매번 새로 쓰게 했다. 리스크가 사라지고, "나만을 위해 골라준"이
"나만을 위해 쓰인"으로 오히려 강해진다.

### 6-4. 실패 처리 기준

| 상황 | 처리 | 사용자에게 보이는 것 |
|---|---|---|
| 빈 입력 / 10자 미만 | 프런트에서 차단 | "조금만 더 자세히 적어주세요. 길수록 정확해져요." |
| 500자 초과 | 실시간 카운터 경고 + 제출 차단 | 글자수 표시가 경고색으로 전환 |
| API 오류 (4xx/5xx) | 상태 코드별 메시지 | "지금은 곡을 찾지 못했어요. 잠시 후 다시 시도해주세요." |
| 요청 과다 (429) | 별도 안내 | "지금 요청이 많아요. 잠시 후 다시 시도해주세요." |
| 15초 초과 | `AbortController`로 중단 | "응답이 지연되고 있어요. 잠시 후 다시 시도해주세요." |
| 검증 통과 0~1곡 | 키워드 검색으로 보충 | "정확히 맞는 곡이 적어서, 키워드로 찾은 곡을 함께 담았어요." |
| 그래도 결과 없음 | 재입력 유도 | "상황이나 분위기를 조금 더 구체적으로 적어보시겠어요?" |
| 위기 표현 감지 | 추천 중단 | 상담 안내(자살예방 상담전화 109 · 정신건강 상담 1577-0199) |

### 6-5. 결과 더 보기 vs 조정

두 동작을 명확히 구분한다.

| | 동작 | 무드 |
|---|---|---|
| **결과 더 보기** | 방금 본 곡을 제외 목록에 넣고 재요청 | 그대로 |
| **조정** | 원래 입력 + 조정 문구로 재요청, 제외 목록 초기화 | 방향이 바뀜 |

제외 목록은 **세션 메모리에만** 존재한다(새로고침 시 소멸). 취향 추론이 아니라
"방금 본 것을 또 보여주지 않는" 페이지네이션에 가깝다.

## 7. 데이터 정책 — 기록은 하되, 반영하지 않는다

**검색 기록은 남긴다.** 자연어 입력은 재현이 어렵다. "새벽에 창문 열고 운전할 때,
근데 너무 처지진 않는" 같은 문장은 나중에 똑같이 다시 쓸 수 없다.
그래서 검색 문장 + 결과 곡 + 창작 문장을 통째로 저장한다.

**하지만 다음 검색에 반영하지 않는다.** 과거 이력으로 결과를 조정하면,
이 서비스가 2-2에서 비판한 바로 그 구조 — 사용자를 자기 이력에 가두는 추천 — 를
스스로 반복하게 된다. **지금 입력한 문장이 유일한 기준**이다.

| 항목 | 정책 |
|---|---|
| 저장 위치 | 브라우저 localStorage (서버 전송 없음, 로그인 없음) |
| 저장 범위 | 검색 문장, 조정 문구, 무드 요약, 곡 목록, 창작 문장 |
| 최대 보관 | 최근 30건 |
| 추천 반영 | **없음** |
| 사용자 제어 | 개별 삭제 · 전체 삭제 · 텍스트 내보내기 · 같은 문장으로 재검색 |

## 10. 기대 효과 및 검증 방법

> 근거 없는 단정 대신 **가설 + 측정 방법**으로 정리한다.

| 가설 | 측정 지표 |
|---|---|
| 이름으로 검색할 수 없던 취향이 실제 결과로 이어진다 | 미리듣기 재생률, 음원 링크 클릭률 |
| 입력이 길수록 만족도가 오른다 | 입력 글자수 구간별 재생률 비교 |
| 자연어 재현이 어렵기 때문에 기록의 재사용 가치가 있다 | 검색 기록에서 "다시 검색" 실행 횟수 |
| 조정 기능이 이탈 대신 재시도를 만든다 | 결과 노출 후 조정·더 보기 실행 비율 |

측정은 Vercel Analytics(방문/세션) + 프런트 이벤트 카운트로 수집한다.

## 11. 향후 확장 (선택)

1. 결과 카드를 이미지로 저장 / 인스타그램 스토리 공유
2. 미리듣기 완청률·스킵률 수집 (현재 미구현 — 취향 반영에 쓰지 않는다는 원칙과 충돌하지 않는 범위에서 품질 측정용으로만)
3. 다국어(영문) 입력 대응
